## 4. 設計上の知見

### 4.1 シミュレーションを描画から分離した効果
- `RoundSimulation` は純粋なTypeScriptで、固定サブステップ (1/240秒) とswept判定 (前ステップから今回の位置までをcapsuleとして判定) で動く。描画フレームレートに依存しない。
- 描画をPhaserからThree.jsへ全面的に差し替えても、domain層とRoundSystem、テスト73件は無変更で通った。
- Validation、テスト、E2Eの判定がすべて同じシミュレーションを使うため、「Validationを通った問題が本番では避けられない」というズレが起きない。
- 動く要素がない区間は次のイベント時刻まで早送りする。Validationは1問あたり100〜150回のシミュレーションを行うが、10ラウンド分の生成は体感で一瞬に収まる。
- 入力時には `advanceTo(入力時刻)` を呼んでから入力を適用する。フレームの途中で入力されても、その正確な時刻で処理される。

### 4.2 Hazardの「解決」判定
- 当初は「全Hazardが消滅したら回避成功」と判定していた。しかし弾は画面外へ出る前にラウンドが終わるため、直線攻撃系がすべてValidationに落ちた。
- 「Playerの位置を通過済みなら解決済み」とする `mainThreatsResolved()` を導入して解消した。弾の射程も、画面外へ出るまでの距離でClampしている。

### 4.3 Anchor方式とValidationの前提
- 本命の攻撃方向・位置は、最初の本命Telegraph時点のPlayer位置 (anchor) を基準とした相対値で生成する。
- Validationは、Playerが初期位置から動いていないという前提でシミュレーションする。Playerが移動していても相対的な形はほぼ同じだが、画面境界の影響だけは変わる。
- 画面端に寄った状態で安全側が画面外になる問題 (ENC-012, 021) は、`safeHint` を使ってTelegraph表示前に左右 / 上下を反転する。表示前の決定なので「後出し」には当たらない。
- **未対応**: `safeHint` を持たないEncounterでの極端な位置 (例: 四隅) は保証していない。

### 4.4 「Flash必須」問題が歩きで避けられる問題
- 仕様書の暫定値 (例: ENC-001 の幅70、弾速900、予兆250ms + 飛翔500ms) では、反応250msで歩けば回避できてしまう。
- 対策として次の判定基準を設けた。

  | 対象 | 基準 |
  | --- | --- |
  | Flash問題の成立 | 反応200msでFlashし、安全地点が存在すること |
  | walkable判定 | 反応300msで歩いて避けられる生成は、最大40回まで再抽選する |
  | Move問題の成立 | 反応350msで歩き始めて回避できること |

- あわせて ENC-001, 006, 010, 012, 013, 016, 017 の弾速・幅・予兆時間を厳しめに調整した。
- 調整後、各難易度で60 Seedずつ生成したときの「walkable」率 (再抽選前の1回目):

  | ENC | budget 1.0 | 2.0 | 3.2 | 使用Tier |
  | --- | --- | --- | --- | --- |
  | 001 | 93% | 17% | 0% | 1 |
  | 006 | 98% | 50% | 0% | 2 |
  | 012 | 38% | 0% | 0% | 2 |
  | 013 | 45% | 0% | 0% | 2 |
  | 016 | 75% | 12% | 0% | 3 |
  | 017 | 98% | 0% | 0% | 3 |
  | 010 / 008 / 020 / 021 | 0% (010のみ1.0で87%) | 0% | 0% | |

- R1〜R2の ENC-001 は40回再抽選しても約6%の確率でwalkableな問題が残る (再抽選に全部失敗した場合は、成立する問題のうちwalkableなものを採用する)。
- ENC-003 は budget 3.2 だと40%が「歩きで回避不可」になるが、Tier 1 なので budget 1.7 以下でしか出題されない。

### 4.5 視覚Cueの統一ルール
本命とFakeを学習で区別できるよう、色の意味を全Encounterで統一している。新しいEncounterを追加するときもこのルールを守ること。

| 色 | 意味 |
| --- | --- |
| 赤 | 実際のHitbox (この色だけが当たる)。例外: 米倉のQ3、アリのE、クリッツブランクのQは範囲を表示しない |
| 橙 | 照準 / 追尾中 (Lock前)。Lockすると赤に変わる。Fakeのマーカーも橙で、赤に変わらない |
| 黄 | 敵の詠唱glow。本命の前にもFakeでも出る |
| 白 | 安全Gapの形状マーカー、敵の踏み込み姿勢、無害なDash軌道、Playerの当たり判定の輪 (半径18) |
| 紫の輪 | 敵の当たり判定の輪 (半径20。クリッツブランクは22) |
| 橙の輪 + 白い蒸気 | クリッツブランクのW (加速中) |
| 桃 | アリのE (ハートの弾) とRの残像。頭上を回る水色の狐火 = アリのRの残り回数 |
| 金の輪 | CS可能なミニオン |

### 4.6 その他の実装上の注意
- `buildEnemyPath` は ENEMY_MOVE / STEP_IN イベントから敵の移動経路を決定論的に作る。敵の位置はSeedだけで決まる (Dash中だけは例外で、anchorに依存する)。
- Neutral中の敵移動は、本命開始の1.3秒以上前に終わるよう配置している。敵が発射元になる攻撃の起点を安定させるため。

### 4.7 3D描画の設計
- **3パスで描画する** (`createGame.ts` のループ)。

  | 順 | シーン | 内容 | 深度 |
  | --- | --- | --- | --- |
  | 1 | world | 地形・木・岩・タワー (静的) | あり |
  | 2 | overlay | 危険領域・照準・Hitbox輪・影などの地面図形 | テストなし (常に地形の上に見える) |
  | 3 | actors | キャラ・ミニオン・弾・爆発 (pass 2の後に深度をクリア) | あり (キャラ同士のみ) |

  ジャングル台地 (高さ26) が画面端に重なっても、危険領域が地形に隠れない。「Telegraphは必ず見える」という公平性の要件を優先した設計。
- **危険領域はY=0平面に描く**: 当たり判定と同じゲーム座標で描く。地面に貼る図形が実Hitboxで、立体の弾や壁は装飾という位置づけ。マウスも同じY=0平面へのレイキャストで座標に変換するため、クリック位置・Flash方向・判定が一致する (E2Eで誤差なしを確認)。
- 川底は-4と浅くしてある。図形をY=0に描くことで、川の中では見た目に数単位の視差が出る。深くすると視差が増えるので注意。
- **カメラ**: 仰角58°、方位45° (青タワー側 = ゲーム座標の -x 方向へ回す)、画角26°の固定カメラ (追従なし)。値は `createGame.ts` の `CAMERA`。
  - 画面に収める範囲を `CAMERA.frame` (x 140〜860, y 40〜560) で指定し、その四隅が収まる距離を二分探索で求める。さらに上下の余白が均等になるよう、注視点を視線方向へずらす。画面サイズが変わるたびに再計算する。
  - 45°回した状態でプレイ範囲 (1000x600) の四隅まで収めると引きすぎてキャラが小さくなるため、攻防が起きる中心エリアに絞った。両者の初期位置、上下端からの攻撃の通り道、スイープのGapが入る範囲。
  - 霧はカメラ距離に合わせて設定する (距離の1.15〜2.4倍)。固定値だと、カメラを引いたときに全体が霧で暗くなった。
  - 画角を広げると台形歪みで手前が広がり、プレイ範囲が小さく映る。
  - 地面は2800四方で作り、斜めの視点でも画面の隅まで地形が見えるようにしている。
- **陰の見た目**: `shadeAt(y)` が、視界の境界 (y<114, y>486) から外側へ最大72%暗くなる係数を返す。地面・結合済みの装飾・水面の頂点カラーにかけて暗くしている。ライトや後処理は使わない。
- **ブッシュの見た目**: `world.vision.brushes` の楕円 (上: 中心 (460, 4)、下: 中心 (537, 558)、半径 140×30) に草を敷き詰める。見た目の範囲は視界判定の楕円と一致させている。位置は、ユーザーがスクリーンショットに描いた赤丸を、カメラの投影から逆算して決めた (`window.__flashCheckView.worldToClient` で格子点を投影し、最も近い点を探した)。

### 4.8 相手チャンピオンの移動AI
- **ロジックはdomain層**: `RoundSimulation.updateEnemy` / `decideEnemy`。敵の位置は「敵が撃つ攻撃の発射位置」として採点に効くため、描画ではなくシミュレーションで動かす。乱数は `${encounter.seed}:${definitionId}:enemy-ai` から作り、同じSeedと同じ入力なら同じ動きになる。
- 以前は生成時に敵の移動経路 (`enemyPath` / `ENEMY_MOVE`) を決めていたが、Playerの位置に反応できないため廃止した。踏み込みのFake (`STEP_IN`) も、その時点の敵の位置からPlayerへ向かう動きとしてシミュレーション内で処理する。
- **時間の区切り**: 1ステップは「4.17ms・敵の次の判断時刻・次の立ち止まり開始」のうち最も早いところで区切る。判断と停止のタイミングが描画の刻みや入力のタイミングに左右されないようにするため。敵が止まっていてほかに動くものがなければ、従来どおり早送りする。
- **出題生成への影響**: 本命の時点での敵の位置は生成時には分からない。
  - ラウンド長の見積もり (弾が届き切るまで) は、追従レンジの上限で計算する。
  - 回避の猶予は、敵がレンジの最短距離 (下限 - 30) から撃った場合でも確保する (`enemyMinLeadMs`)。Flash問題は「予兆 → 着弾」が0.38秒以上、歩き問題は「反応0.35秒 + 判定の外まで歩く時間 + 0.15秒」以上になるよう、予兆時間 (ENC-013はLock → 発射) を延ばす。Validationは敵の動きの1パターンしか確かめられないため、生成側で最悪ケースを保証している。
  - レンジを縮めた際、敵の最初の判断が早送りの後まで遅れるバグが見つかった (初期距離が範囲外だと、しばらくその場に立っていた)。ループの先頭で `updateEnemy(0)` を呼んで修正済み。
- **ENC-017 (交差する2本の弾)**: 2本目の発射点を、実行時の「敵 → Player」の線を交差角だけ回した向きで計算する (`LineOrigin` の `CROSS`)。どこに敵がいても交差角が保たれる。
- **性能**: 敵が常に動くため、Validationのシミュレーションで早送りがほとんど効かなくなった。ゲーム開始時の10ラウンド生成は50〜90ms (問題なし)。テスト全体は約1秒 → 約11秒に増えた。主に、Encounterごとに全候補をシミュレーションするテストの分。

### 4.9 相手チャンピオン「米倉」
- **出題の流れ**: `buildEncounterSequence` がデッキ (標準の問題) を作った後、ラウンドごとに `assignChampion` で相手を抽選する。米倉なら `YONEKURA_REPLACEMENTS` で差し替える。`GeneratedEncounter.champion` に相手を持つ。デッキの条件 (Flash 3以上など) は差し替え前のデッキで満たしている。
- **スキルの実装** (すべてRoundSimulation内。採点に効くため):

  | スキル | 実装 | 予兆 | 当たり判定 |
  | --- | --- | --- | --- |
  | Q1/Q2 | `YONE_Q_VISUAL` (演出のみ)。一番近い味方ミニオンへ突く。2回目の後、Q3を使うまで剣のまわりに風がまとう | なし (赤は出さない) | なし |
  | Q3 | `DASH` (`style: "q3"`, `length: 440`)。発射位置から固定距離を駆け抜け、先端に竜巻 | **範囲は表示しない** (本家どおり)。手がかりは詠唱の光・剣の風・竜巻のみ | 通り道全体 |
  | R | `DASH` (`style: "r"`, `length: 560`, 速度5000 = ほぼ一瞬)。斬り抜けた後に閃光 | 太い赤い帯 (0.5〜0.65秒) | 通り道全体 |
  | E | `YONE_E`。半透明の「体」を残して前へ出る (Playerから110より近づかない)。`returnAtMs` に体へ戻る | 白い輪 (構え) | なし |

- **Eの位置管理**: 敵の位置の優先順位は「Eの帰還中 → 突進中/突進の終点 → Eで前に出た位置 → 踏み込み → 移動AI」。帰還が終わるとEの状態を消し、それ以前の突進は `superseded` にして、終点に縛られないようにする。Eの往復中は移動AIを止める (立ち止まる時間帯に含める)。
- **Q3は範囲を出さない**: ユーザー指示 (本来見えないため)。「赤 = 実Hitbox」の原則の例外になる。反応時間の基準 (`threatVisibleMs`) も、範囲ではなく「詠唱・突進する米倉本人が視界にいるか」で判定する。Rは範囲を表示したまま。
- **公平性**: E→Q3 / E→R はEで近づいた後に撃つため、追従レンジの最短距離による猶予計算 (`enemyMinLeadMs`) が使えない。予兆時間を直接、最低0.38秒にしている。
- **出題の検証**: 米倉の6問はいずれも、どの難易度でもValidationを通る (40 Seed × 3難易度で確認)。テスト (`tests/yonekura.test.ts`) で、抽選率・差し替え・Eの往復・Q3の固定距離・Rの終点・E→Rの帰還・正しいFlashで避けられることを確認している。
- **新しいキャラの追加手順**: ① `types.ts` の `ChampionId` に追加 ② `definitions.ts` に問題定義・差し替え表 (`*_REPLACEMENTS`)・出題しない問題 (`*_UNSUPPORTED`) ③ `generators.ts` にビルダー ④ 必要なら `RoundSimulation` に新しい動き (イベント種別) ⑤ `models.ts` にモデル、`GameView` に演出 ⑥ `balance.ts` の `champions.chances` に確率、`session.ts` の `assignChampion` の表に追加。表示名は `championName()`。

### 4.10 相手チャンピオン「アリ」
- **問題と差し替え** (`TAMAMO_REPLACEMENTS`):

  | 元 | アリ版 | 正解 | 流れ | Rの回数 |
  | --- | --- | --- | --- | --- |
  | ENC-001 | TMM-RE | FLASH | (横へのR) → 最後のRで接近 → 近距離E | 1〜3 |
  | ENC-002 | TMM-E-FAR | MOVE | (横へのR) → 最後のRで後ろへ離れる → 遠距離E。0回なら追従レンジのままE | 0〜2 |
  | ENC-013 | TMM-RRE | FLASH | 横へのRで揺さぶる → 最後のRで接近 → E | 2〜3 |
  | ENC-015 | TMM-RBACK | MOVE | (横へのR) → Rで接近 → Rで後退 → E | 2〜3 |
  | ENC-017 | TMM-RBACK-F | FLASH | Rで接近 → Rで後退 → Rで再接近 → E | 3 |

  Rの着地からEの詠唱までの間隔 (0.1〜0.7秒) と、R同士の間隔も抽選する。「Rを使った = すぐEが来る」とは限らない。
- **Rの実装** (`TAMAMO_R` / `castTamamoR`): 着地点は実行時に「Player → アリ の向きを `bearingRad` 回した方向、Playerから `toDistance`」。最大230まで進む (速さ1100、約0.2秒)。着地点がレーン外・画面外に押し戻されて狙いの距離にならない場合は、向きの候補を順に試す。これを入れる前は、レーン端で押し戻されてPlayerに近づきすぎ、Eの着弾まで0.31秒しかない問題ができていた。1ラウンド3回を超えるRは無視する。Rの最中と着地後0.25秒は移動AIを止める。本命の直前のRは、Eを撃つまでその場に留まる。
- **Eの詠唱時間**: 生成時に「Eを撃つ距離の見積もり (最短側)」から計算する (`tamamoWindup`)。FLASH問題は詠唱開始から着弾まで0.38秒以上、MOVE問題は「反応0.35秒 + 横へ歩いて抜ける時間 + 0.15秒」以上になるよう延ばす。TMM-E-FAR でRを使わない場合は、追従レンジの最短距離から撃つ前提になるため詠唱が約0.6秒と長くなる。
- **実測** (何もしない場合、各60 Seed): FLASH問題はEを撃つ距離が約190〜225、着弾まで0.41〜0.49秒。MOVE問題 (Rで後退) は距離約305〜320、着弾まで約0.8秒。
- **Eの射程を460 → 350に短縮** (ユーザー指示)。合わせて遠距離E (TMM-E-FAR) の離れる距離を430〜450 → 310〜330、Rで後退する距離を380〜410 → 300〜320にした (射程外から撃って届かない問題にならないように)。
- **範囲を表示しない**: 赤い帯は描かず、飛んでいく桃色のハートだけを描く。反応時間の基準は「詠唱するアリ本人」か「ハート」が視界にあるか。アリはレーン内にいるため、実際は詠唱開始の瞬間になる。詠唱の黄色い光は他のキャラと共通。
- **魅了**: `hitDisplacement()` がクリッツブランクの引き寄せと共通の形で「当たった位置 → アリの方へ最大42 (速さ70 × 0.6秒)」を返す。RoundSystemは被弾演出の長さだけRESOLUTIONを延ばす。
- **テスト**: `tests/tamamo.test.ts` で、Rの回数 (0〜3回すべてが出ること、3回を超えないこと)、Rに当たり判定がないこと、Rの最大距離、Eを撃つ距離、FLASH / MOVE で避けられること、全難易度でValidationを通ること、魅了の演出の長さ、入力の刻みによらず同じ動きになることを確認している。

### 4.11 ガンク専用の敵「クリッツブランク」
- **位置づけ**: レーンの相手 (標準 / 米倉) とは別に出る3体目の敵。`GeneratedEncounter.ganker` に `"kritz"` を持つ。レーンの相手の抽選はこれまでどおりで、KRZ問題は差し替えの対象外 (どちらの相手とも組み合わさる)。
- **ロジックはdomain層**: `GANKER` イベントで出現し、`RoundSimulation.ganker` が位置を持つ。Qは `LINE_SHOT` (`origin: GANKER`, `style: "hook"`) で、詠唱を始めた時点の位置から、その時点のPlayer位置 (anchor) へ飛ぶ。詠唱を始めたら動かない。

  | ルート | 動き |
  | --- | --- |
  | APPROACH | 陰の中 (境界から30奥) に出現し、W (速度330) で「Playerから止まる距離・edge側へ傾けた向き」の地点へ向かう。地点はPlayerの現在位置から毎ステップ計算する (追いかける) |
  | AMBUSH | 陰の中で、Playerから480〜500の位置に潜んで動かない |
  | RETREAT | APPROACHと同じく近づき、止まって0.5〜0.8秒後に出現位置へ歩いて (速度150) 戻る |
  | PASS | Playerの右330〜380を、上下の陰から陰へWで横切る |

- **止まる位置は必ず視界内**: 止まる位置が陰の境界から30以上内側に入るよう、Playerからの向きの角度の上限を生成時に計算する。そのため右前方 (相手側) の斜め上/下から来る。画面外にはみ出す場合だけ左右を反転する。
- **反応時間の基準**: Qは範囲を表示しないので、「詠唱を始めた本人が見えている」か「伸びていく拳と鎖のどこかが見えている」で `threatVisibleMs` を判定する。APPROACHは止まって詠唱を始めた瞬間、AMBUSHは鎖が陰の境界を越えた瞬間 (生成時に幾何で見積もり、Validationで50ms以内を確認)。
- **射程を520 → 390に短縮** (ユーザー指示)。そのままの速さ800だとAMBUSHの「鎖が見えてから着弾」が約0.3秒まで縮んだため、Qの速さを700に下げた。APPROACHは速さを下げたことで歩いて避けられるようになり全部再抽選されたため、止まる距離と詠唱も詰めた。
- **数値の根拠** (Qの速さ700、幅70、射程390):
  - FLASH (APPROACH): 止まる距離235〜255、詠唱0.2〜0.22秒。着弾まで約0.46〜0.51秒で、0.3秒反応では歩いて避けられない (再抽選の対象にならない) 範囲。
  - FLASH (AMBUSH): 陰の中の距離365〜375 (射程の端近く)。鎖が見えてから着弾まで約0.37〜0.41秒。陰の中の位置を境界の近く (境界から30奥) にし、斜めに撃たせることで、視界内を通る距離を稼いでいる。
  - MOVE (遠いQ): 止まる距離340〜355、詠唱0.28〜0.3秒。着弾まで約0.7秒あり、0.35秒反応で横へ歩けば避けられる。
  - 当初は止まる距離270〜300にしていたが、易しい難易度で約半数が歩きで避けられたため詰めた。
- **引き寄せ**: 被弾自体は通常どおり当たった瞬間に確定する。`hookPull()` が「当たった位置 → クリッツブランクの正面」を返し、描画側がその間を0.32秒で補間する。RoundSystemは、Qで被弾したときだけRESOLUTIONを `pullMs` だけ延ばす。
- **標準のガンクの廃止**: ユーザー指示でENC-006 (上の川からのガンク) とENC-016 (中央のFake → 川からの本命) を削除し、ガンクはクリッツブランク (KRZ-*) だけにした。上下が固定のENC-006のために入れていたデッキ規則 (「固定方向のガンクを別のガンクの直後に置かない」) も不要になったので削除。ガンクの上下は引き続き直前のガンクと逆になる (`prevSideEdge`)。デッキの「ガンク最低1問」はKRZ問題 (Tier 2) で満たす。
- **HUD**: 開始時の「VS 名前」とHUDにはクリッツブランクを出さない (ガンクの予告になるため)。Final Resultの相手欄にだけ「標準 + クリッツブランク」のように表示する。
- **テスト**: `tests/kritz.test.ts` で、陰からの出現と視界内でのW、詠唱時に見えていること、AMBUSHで本人が最後まで見えないこと、Flash / 歩きで避けられること、2種類のフェイクで当たらないこと、入力の刻みによらず同じ動きになること、引き寄せの分だけRESOLUTIONが延びることを確認している。

### 4.12 ミニオンとCS
- **ロジックはdomain層**: ミニオンの体力推移と攻撃の判定は `RoundSimulation` にあり、CSが採点に入るためSeedで再現できる。`GeneratedEncounter.minions` に、初期体力 (`startHp`) と毎秒の減少量 (`drainPerSec`) を生成時に確定させて持つ。
- 体力は線形に減るので、早送り中も「次に誰かが倒れる時刻」までは一気に進めてよい (`nextMinionDeathInMs`)。逐次stepと同じ結果になる。
- **右クリックの判定** (`RoundSimulation.rightClick`): クリック位置から外周+10以内に生きている敵ミニオンがいて、かつ射程内 (Player中心からミニオン外周まで180) なら攻撃 (`attack`)、そうでなければ `move`。攻撃は「攻撃間隔 → ダメージ」の順に判定し、`attacks` に `hit / kill / cooldown` を記録する。攻撃は行動分類 (MOVE/FLASH) に影響しない。
- **描画**: ミニオンの位置は固定で、一番近い相手側のミニオンへ周期的に踏み込む動きだけ付けている。体力バーはカメラに正対させる。敵の体力が攻撃力以下になると、バーが金色になり足元に金の輪が出る (とどめの合図)。ラストヒット成功時は金色の光が昇る。
- **得点**: `RoundResult.csScore` に本命とは別に保持する。`GameResult.totalScore` = `mainScore` + `csScore`。HUDのScoreには進行中ラウンドのCSも含めて表示する。

### 4.13 視界 (Fog of War)
- **判定はdomain層**: `src/domain/fieldLayout.ts` の `isVisible(p, viewer)`。ブッシュ内の点は、viewerが同じブッシュに入っている場合だけ見える (陰より優先)。それ以外の陰 (`world.vision.shadeTop/shadeBottom`) は常に視界なし。描画と採点が同じ関数を使う。
- **反応時間の基準**: `RoundSimulation` が毎ステップ、本命Hazardの見た目 (予兆の帯・弾・円の縁・Dash軌道・スイープ) のサンプル点が視界内にあるかを調べ、最初に見えた時刻を `threatVisibleMs` に記録する。`recognitionMs` は「描画時刻 → 視界に入った時刻 → 予定時刻」の優先順。描画側からの通知 (`markRecognitionVisible`) は、視界に入る前の時刻だと無視される。
- **Validation**: 何もしない場合でも、予定の認識時刻から50ms以内に本命が視界に入ることを必須にした。初期位置はレーン上なので、上下端から来る攻撃も予兆の帯がレーンに掛かり、すぐ見える。
- **描画での隠し方**:

  | 対象 | 方法 |
  | --- | --- |
  | 地面の図形 (予兆・弾の地面部分・敵の足元の輪など) | ステンシルで切り抜き。`FogMask` が陰の帯と全ブッシュの楕円をステンシル=1 (視界なし) で書き、最後に自分が入っているブッシュだけを0 (見える) で上書きする。`clip=true` の図形は1の場所に描かれない |
  | 立体の演出 (弾・スイープの壁・爆発) | 同じステンシルで切り抜き |
  | 敵キャラ・ミニオン・CS対象・敵影 | 足元の点が見えなければ、モデルごと非表示。背の高いモデルを地面のマスクで切ると、頭だけ欠けるなどのずれが出るため |
  | 自分のキャラ・当たり判定の輪・移動先・Flash/被弾の演出 | 隠さない (`clip=false`) |

- **注意**: three r163以降、`WebGLRenderer` のステンシルバッファは既定で無効。`stencil: true` を付けないと切り抜きが効かない (実際に一度ハマった)。
- Edge Shadow (敵影) は、陰の中では見えなくなるため、視界の境界のすぐ内側 (境界から14) に表示している。暗い紫の半透明。
- **静的装飾の結合**: 木・岩・草むらは個別Meshだと数千drawcallになる。頂点カラー付きの1メッシュへ結合 (`bakeStatic`) した結果、SwiftShader環境で2fps → 19fpsに改善した。揺らす炎とタワーの結晶は結合しない。
- **毎フレームの図形**: `GroundOverlay` / `Effects3D` は単位サイズのジオメトリをMeshプールで使い回し、位置・スケール・色だけを更新する (2D版の即時描画と同じ書き方)。リング状の図形は、太さ/半径比 (0.01刻み) ごとにジオメトリをキャッシュしている。
- **地形の高さ**: `field.ts` の `groundHeight` が、川の窪み (`riverDepthAt`。レーンの手前26単位で浅くなって途切れる)・ジャングル台地・崖の凹凸を決める純粋関数。キャラの表示高さ (`standHeight`) もこれを使う。装飾の乱数は固定Seed (`field-decoration`) で、毎回同じ見た目になる。
- **ヘッドレスE2Eの注意**: GPUなしのSwiftShaderではフレームレートが低く、スクリーンショット1枚に数百msかかる。本命の直前にスクリーンショットを撮ると入力が間に合わず被弾する。入力判定の確認と見た目の確認は分けて行うこと。起動オプションに `--use-angle=swiftshader --enable-unsafe-swiftshader` が必要。
- **狙った瞬間の撮影**: Playwrightの `addInitScript` で `performance.now` を仮想時計に差し替え、「時計を進める → 2フレーム待つ」を繰り返すと、描画が遅くても任意のラウンド時刻で止めて撮影できる (ゲームループが `performance.now()` だけで時刻を得ているため)。

## 5. 既知の制約・リスク

| 項目 | 内容 | 影響 |
| --- | --- | --- |
| タブ非表示 / 復帰 | `performance.now()` が大きく進み、Playerが静止したままシミュレーションが早送りされるため、ほぼ確実に被弾する | ポーズ機能なし |
| 認識時刻の精度 | 描画フレームの開始時刻を採用しており、実際に画面へ表示された時刻ではない (最大1フレーム程度の差) | 反応時間がわずかに長めに出る可能性 |
| 四隅などの極端な位置 | `safeHint` を持たないEncounterでは回避可能性を保証していない | 極端な位置取りをしたときだけ |
| favicon | 404 (コンソールにエラーが1件出る) | 実害なし |
| 開発用フック | 開発サーバーでは `window.__flashCheck` (RoundSystem) と `window.__flashCheckView.worldToClient` を公開している (本番ビルドでは無効) | E2E専用 |
| 実GPUでの性能 | ヘッドレス (SwiftShader) でしか計測していない。影 (2048, PCFSoft) が最も重い | 低スペック機では影の品質を落とす設定が必要かもしれない |
| バンドルサイズ | JSが約820kB (gzip 224kB)。Viteが500kB超の警告を出す | 初回ロード時間 |
| 画面外のプレイ範囲 | 斜めカメラでは、プレイ範囲の隅 (例: 左上・右下の角付近) が画面外になる。上下端から来る攻撃の発射点は画面外になることがあるが、Playerの近くの予兆と弾は画面内で見える | 極端な位置取りをしたときだけ |
| Playerが陰に入った場合 | 陰の中にいると、足元に来る攻撃 (円など) も視界外になり見えない (陰は入っても見えない仕様のため) | 自分から陰に入ったときだけ。Validationは初期位置 (レーン上) で行う |
| 敵側から見た視界 | 敵がPlayerを見えているかは扱わない (敵の攻撃は常に生成どおり発生する) | ブッシュに隠れて攻撃を避ける遊び方はできない |
| 地形と攻撃の見た目のずれ | 上下端のSide Gankは、陰のジャングル台地の上から飛んで来るように見える。川の中では地面図形との視差が数単位ある | 判定には影響なし |

## 7. 開発時の手順メモ

- **バランス確認**: Encounter定義ごとに複数Seedで `generateEncounter` と `validateEncounter` を実行し、ok数・walkable数・エラー内訳を集計すると傾向が分かる (4.4節の表はこの方法で作成した)。
- **ブラウザでの自動確認**: 開発サーバーを起動したうえで、`window.__flashCheck` から `phase`、`encounter.recognitionMs`、`encounter.expectedAction`、`sim.player.pos` を読み取り、本命開始の直後に入力する。
- **Seedの決定性**: ゲームロジックで `Math.random()` を使わないこと。乱数はラウンドごとに `${seed}:round:${i}:${encounterId}`、デッキ選択は `${seed}:deck` から派生させている。
